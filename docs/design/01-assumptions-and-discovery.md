# 01. Assumptions and Critical Discovery Questions

This document lists what we do not yet know, what we have assumed so design
can proceed, and the documents we need before any real analyzer driver is
written. Labels follow [docs/README.md](../README.md).

## 3. Working assumptions

Each assumption is a placeholder. When a discovery answer arrives, update the
assumption and every document that cites it.

| ID | Assumption | Consequence if wrong | Closes with |
|---|---|---|---|
| A-1 | The middleware runs on a hospital-managed **virtual machine** with no physical COM port. RS-232 instruments are reached through a **serial device server** (RS-232 to TCP, raw socket mode) placed within 15 m of the analyzer. | If a physical server with COM ports is used, the serial transport is configured instead. Both transports are designed. | D-13, D-17, D-23 |
| A-2 | Target CPU architecture is **x86-64**. | Native serial module prebuilds and the bundled Node.js must be rebuilt for ARM64. | D-17 |
| A-3 | The e 411 will run in **cobas® protocol type** with **real-time** inquiry and automatic upload enabled. cobas® type sends calculated tests and distinguishes rerun results (status `C`) [DOC e411 HIM E-15, E-16]. | If Elecsys® type is kept, the alternate record layout is used; both are parsed. | B-2 |
| A-4 | The middleware is the **source of truth for analyzer orders**. Analyzer queries are answered from the local database only, never by a synchronous HMIS call, so a reply always meets the analyzer's timeout. | None expected. | n/a |
| A-5 | The HMIS is the **source of truth for patients, encounters, and orders**. Manual registrations during downtime are provisional until reconciled. | If the hospital wants the middleware to be the master for some data, reconciliation rules change. | D-6 |
| A-6 | Results are released to the HMIS **only after a person releases them**. Autoverification is off and can only be enabled per test after documented laboratory validation; when it is on it approves, and a person still releases (A-19). | n/a (policy) | Lab director |
| A-7 | Expected peak load is below **2,000 samples/day** and **20 result messages/minute** per instrument. Sizing in [11](11-installation-and-runbooks.md) uses this. | Re-size. | D-9 |
| A-8 | The HMIS supports some idempotency mechanism (idempotency key, or a stable external result ID we can query). | Without it, "request succeeded but response lost" can only be resolved by human reconciliation. See [08](08-durable-processing.md) §7. | D-5, D-7 |
| A-9 | Browser users are on the hospital intranet; no internet exposure. | Internet exposure would need a separate threat model. | D-23 |
| A-11 | The c 111 will run in **REALTIME** communication with "Send Order Query = ALWAYS", "Send Result Mode = COMPLETE", checksum ON, and Sample ID handling **"Order ID = Sample ID"**. Handshake (XON/XOFF or OFF) is set to match the device server. | If Grouped Sample ID mode is required, matching must strip the 3-character extension; not in the MVP. | B-9 |
| A-12 | Instruments beyond the e 411, c 111 and Mindray get no model-specific driver in the first release. An administrator can register them with a generic result-only profile ([14](14-adding-instruments.md)), but they stay out of clinical use until each has its own manual, an interface test and lab acceptance. | Re-plan if the lab needs host query on another instrument first. | D-26 |
| A-13 | Local accounts hash passwords with **scrypt** (N=2^15, r=8, p=1) from the Node.js standard library, not the argon2id named in [10](10-security-and-audit.md) §3, so the offline install needs no native module. Both are memory-hard. Hospital sign-in through OIDC is built (A-17); LDAPS is not. Local accounts stay for break-glass use. | Switch to argon2id if the hospital's policy names it: the hash format carries its algorithm, so old hashes keep working during the change. | D-17, hospital IT security |
| A-14 | Specimen labels carry a **Code 128** barcode of the accession number (`L` + YYMMDD + 5 digits, 12 characters, within the 22-character limits above) on a **50 x 25 mm** label printed from the browser, with name, MRN, birth date, sex, specimen type and tests. Specimen types come from the HMIS order line as given. | Change symbology, size or fields to the hospital's label specification; a thermal-printer language (ZPL or EPL) would replace browser printing. | B-8 |
| A-15 | During HMIS downtime the lab registers a **provisional patient** (`PROV-000001`) and a **downtime order** (`DT-000001`) by hand, choosing tests from the local codes already known (HMIS code map and active instrument mappings). Results on a downtime order are **held**: they can be reviewed and approved but not released. Sending with downtime identifiers is not built. One technologist or approver reconciles each order to the HMIS order, re-entering their password; specimens and results move to the HMIS order's matching tests, and the provisional patient is marked merged, never deleted. | If the HMIS accepts results against downtime identifiers, add that as a configurable option. If policy wants two people for reconciliation, add the same check as for unmatched results. | D-6, D-7 |
| A-16 | The W-10 audit export is **JSON lines plus a manifest** (count, first and last sequence number, SHA-256 of the lines), with each event's `prev_hash` and `hash` so a contiguous range can be checked independently. It is **not signed**: signing needs a key held by the hospital, not the vendor ([10](10-security-and-audit.md) §8). One export holds at most 50,000 events. Search and export are for the auditor role only. | Add a detached signature once the hospital names the key and tool. | Hospital IT security |
| A-17 | Hospital sign-in is **standard OIDC** (code flow, PKCE), because the IdP is not yet known (D-19); nothing product-specific is assumed. Groups must arrive in the ID token, and the IdP must honour `prompt=login` with `max_age=0` and send `auth_time`, because those accounts confirm approve, release, correct and account changes by signing in again at the IdP. Each confirmation allows **one** such action within 5 minutes. Without `auth_time` those actions are refused for SSO accounts, not waved through. Roles follow directory groups at every sign-in. | If the IdP cannot re-prompt, decide with the lab director between a separate signing password held here, or local accounts for approvers. If groups only come from userinfo, add that call. | D-19, hospital IT |
| A-18 | **Critical limits come only from the lab.** The middleware ships with none and suggests none; nothing is flagged until an approver enters the lab's own limits with their source. A value is critical when it is **strictly** below the low limit or above the high limit. Units are compared as exact text; no conversion. When the patient's sex or birth date is unknown, every limit for the test applies, so nothing is missed. Age bands count months as 30 days and years as 365. A censored value ("<0.5", ">1000") is critical only when its bound settles it. Qualitative results (for example a positive culture) have no limits yet. Limits apply to values that arrive after they are saved; earlier versions are not re-checked. The escalation timer is shown, but there is no target time and no automatic escalation to another person. | If the lab's policy treats the limit value itself as critical, change the comparison. Add a target time and escalation steps once the lab names them, and SMS or e-mail once the hospital gateway is known. | Lab director, D-27 |
| A-19 | **Autoverification is off for every test** and ships with no rules. An approver (the lab director) turns one test on at a time with an inclusive low-to-high range in exact units, names the lab's validation report, and confirms how QC is covered, because **the middleware checks QC only when the rule asks for it**: a rule may require QC in range for that test on that instrument within 1 to 168 hours (A-21). A test with a delta rule (A-20) is held when its delta check flags; a test without one is not compared with earlier results. Only the first instrument value of a new result is considered. It passes when every check passes: first value, instrument cleared for clinical use, plain number, units equal, inside the range, no abnormal flags, no instrument flags, not edited on the instrument, not critical (including units that differ from a critical limit), no delta flag. A message without per-observation metadata is treated as flagged. A pass **approves** the result as `system:autoverify`; **release stays with a person**, whose name goes to the HMIS as the releaser. Every decision is stored with all its checks. | Require the QC window and a delta rule before letting autoverified results release without a person; decide with the lab director whether the HMIS should see "autoverified" in the submission once its format is known. | Lab director, D-1 to D-6 |
| A-20 | **Delta rules come only from the lab**, one per test: a largest change in the rule's units, as a percentage of the previous value, or both (either crossed flags), and a window in days. The previous value is the selected version of the same patient's most recent **approved** result for the same local test code (approved, queued, sent, confirmed, failed delivery or corrected), collected inside the window before this specimen; results still waiting for review are not a baseline. Only plain numbers are compared; units must match exactly or the version is marked "not compared". The flag (`EXCEEDED`, `UNITS_DIFFER`) is set once when a version is written and does not block approval; autoverification holds any flagged value. Patients are matched by the HMIS patient record only, so a provisional downtime patient has no history until reconciled. | Make an exceeded delta block approval, or ask for a reason, if the lab's policy wants it. Add qualitative deltas (for example blood group) once the lab names them. | Lab director |
| A-21 | **QC ranges come only from the lab**: one acceptable range (inclusive) per instrument, test and control, the control named by lot, name, or both, exactly as the instrument reports them (e 411 C-record or "QC additional information" setting, Mindray PID-3 lot, the QC sample ID for generic profiles). Each QC result is checked once at intake and kept with its outcome (`IN_RANGE`, `OUT_OF_RANGE`, `RULE_VIOLATION`, `UNITS_DIFFER`, `NO_RANGE`, `NOT_NUMERIC`); QC results without a range are kept but not judged. A control's warning stays on the dashboard until a later result for it passes. Westgard rules are optional per range (A-23); each range has a Levey-Jennings chart (W-15). Nothing stops patient results when QC fails: the lab's QC procedure decides that, except that an autoverification rule with a QC window holds results. Whether each installed instrument sends QC results to the host at all, and how it names the control, is to be confirmed in interface testing. | Confirm with the lab director whether QC review happens here or on the instruments. | Lab director, B-6, B-9, B-3 to B-5 |
| A-22 | **Turnaround times** come only from times the middleware records: order time (from the HMIS), collection and receipt times on the specimen (as entered at collection and receipt), the first stored value, and the first approve, release and accepted-delivery events. Each step uses the first occurrence, so corrections and resends do not move it. Results are grouped by the day of collection in the lab's time zone (A-24; order time when there is no collection time). Figures are the median and 90th percentile (nearest rank). Missing times leave a step out; backwards times are left out and counted. **Targets come only from the lab**, measured from receipt in the lab to release (the part the lab controls), one per test and priority with "every test" and "every priority" allowed; the most specific applies. The report counts results released within target and late ones (released late, or unreleased and already past it); the overdue list and dashboard show unreleased results past target, most overdue first. A specimen with no receipt time has no target clock. The CSV export holds accession numbers and times, never names or MRNs, is limited to approvers and auditors, and is audited. | Measure targets from collection instead, if the lab's policy does; confirm the lab's time zone setting (A-24). | Lab manager |
| A-23 | **Westgard rules are off unless the lab turns them on** for a QC range, by entering that control's target mean and SD (from the lab's own QC data or the insert; none shipped) and choosing among 1-2s, 1-3s, 2-2s, 4-1s and 10x. Each QC result with a mean and SD keeps its z score. 1-2s is a warning only; any other rule broken makes a result inside the range `RULE_VIOLATION`, which counts as failed QC on the QC page, the dashboard and the autoverification QC window. **Assumptions**: the rules look along one control's own series across runs, never across controls within a run, because each control arrives as its own QC message and there is no reliable run to group them by; so R-4s (a within-run rule) is not offered. The series is the control's earlier accepted (`IN_RANGE`) results for that range, so a rejected result does not count again and a rerun after corrective action starts clean. A new mean or SD is a new range, which starts a new series. | Add R-4s and across-level 2-2s once the lab confirms how its instruments group controls into runs; confirm the rule set and the treatment of rejected results with the lab director. | Lab director |
| A-24 | **One time zone for the lab**, set by `LIMS_TIME_ZONE` (an IANA name such as `Africa/Nairobi`; default `UTC`; an unknown name stops the web service at start and fails `lims config check`). Every time is still stored as an instant in UTC. The setting changes only (1) how pages show times, always with the clock named (`2026-11-04 08:10 GMT+3`, or `UTC`), (2) how a typed time is read (the collection time), and (3) where report and audit-search days start and end. Exports (turnaround CSV, workload CSV, audit export) keep machine times in UTC (ISO 8601), except that the workload CSV's day column is the lab's day. In a daylight-saving gap a typed time moves forward by the gap; in an overlap the earlier instant is used. Dates of birth and instrument test dates are calendar dates, not times, and do not change. Report days use the time the middleware recorded (arrival, collection), not the instruments' own clocks. | Set `LIMS_TIME_ZONE` to the hospital's zone at install. | Lab manager, IT |
| A-25 | **Reference ranges come from the instrument or the lab, never from the middleware.** The lab may enter its own ranges per test, sex (everyone, F, M) and age band (days, months or years; a month is 30 days and a year 365), inclusive at both ends, in exact units, naming the source; none are shipped. Where a lab range applies it is shown instead of the instrument's text. Unlike critical limits, a range applies only when it certainly fits the patient: a sex-specific range needs the recorded sex and an age band needs the birth date, so an unknown patient never gets another group's range; among those that fit, sex and age together beat one of them, which beats neither, and a narrower age band beats a wider one. A range covers values stored while it was in force, so adding or retiring one never changes an earlier report. The below or above mark is for people only: it is not stored, not sent to the HMIS, and autoverification does not use it (it goes by the instrument's own flags). | Enter the lab's verified ranges for tests whose instruments send none (for example where the c 111 or a generic analyzer omits them); decide with the lab director whether the HMIS should receive the lab's range once its format is known. | Lab director, D-1 to D-6 |
| A-26 | **Comments on results** are free text (2 to 500 characters, whitespace collapsed) from technologists and approvers. Each is either for the lab only or printed on the result report under the value; only an approver may add or withdraw a report comment, so nothing reaches paper without an approver. Report comments print only on approved lines. A comment is never edited or deleted (a database trigger enforces it); a wrong one is withdrawn with a reason, is struck through on the result page, stops printing, and stays in the audit trail. **Comments are not sent to the HMIS**: its format for result notes is not known. The lab can keep standard comments to pick instead of typing (A-27). | Confirm whether and how the HMIS accepts result comments (NTE or a notes field) once its interface is known; decide whether report comments added after approval should need a new approval. | Lab director, D-1 to D-6 |
| A-27 | **Standard comments are the lab's own**, entered by approvers (with their password) as a code of 2 to 12 letters, digits or hyphens and a text of 2 to 500 characters, offered on every test or on one test; none are shipped. A code has one active comment at a time. Picking one on a result copies its text into an ordinary result comment (A-26), so it follows the same lab-only or on-the-report choice and approver rule, and retiring or rewording a standard comment never changes a comment already made; the audit records which code was used. A comment is picked or typed, not both. | Agree the lab's standard comments and their wording with the lab director before go-live. | Lab director |
| A-10 | Mindray data arrives over TCP with MLLP framing [DOC Mindray §1]. Which side listens is configurable in the adapter until confirmed. | n/a | B-4 |
